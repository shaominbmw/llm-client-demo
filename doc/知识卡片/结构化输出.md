# 知识卡片｜结构化输出（让模型返回可信的 JSON）

**标签**：LLM / JSON / 数据抽取　**建立**：2026-11-21

## 一句话

结构化输出 = 让模型输出的不是「一段话」，而是**一个能直接反序列化成对象的 JSON**。
它是 RAG 字段抽取、Agent 工具参数、报表生成的地基。

## 三个层次（可靠性递增）

| 层次 | 做法 | 保证什么 |
|---|---|---|
| 1. 提示词约束 | Prompt 里写「请输出 JSON」 | ❌ 什么都不保证 |
| 2. `json_object` | `response_format: {"type":"json_object"}` | ✅ 是合法 JSON，❌ 字段结构不管 |
| 3. `json_schema` | 传完整 schema + `strict: true` | ✅ 字段、类型、枚举都对 —— **但厂商支持度不一** |

## 真实踩坑：schema 不是万能的

**现象**：给 DeepSeek 传了带枚举的 schema

```json
"severity": {"type":"string","enum":["LOW","MEDIUM","HIGH"]}
```

模型返回：

```json
{"severity":"中"}
```

不是 `MEDIUM`，是中文「中」。反序列化直接炸：

```
Cannot deserialize value of type `Severity` from String "中"
not one of the values accepted for Enum class: [HIGH, LOW, MEDIUM]
```

**原因**：DeepSeek 接受 `json_schema` 参数（返回 200），但**并没有真正强制执行枚举约束**。

**结论**：

> `response_format` 是「请求」，不是「保证」。
> 只要厂商支持度不统一，就必须**把 schema 同时写进提示词**，两层一起上。

## 工程上必须做的五件事

```
1. 强制 JSON 模式        response_format
2. schema 写进提示词      ← 应对「接受参数但不执行」的厂商
3. 抠 JSON               去围栏、去前后废话
4. 反序列化 + 业务校验
5. 失败重试一次          把「具体错在哪 + schema」回灌给模型
```

### 第 3 步：为什么要「抠」

即使要求「只输出 JSON」，模型仍可能给你：

```
好的，以下是抽取结果：
```json
{"a":1}
```
希望对你有帮助。
```

所以**永远不要** `readValue(模型原文)`，先取第一个 `{` 到最后一个 `}`。

### 第 5 步：重试的关键是「说清楚哪里错」

差的写法：「请重新输出 JSON」——模型不知道为什么错，大概率再错一次。

好的写法：把三样东西一起给它

```
你上面的输出不符合要求。具体问题：<异常信息>
必须严格符合这个 JSON Schema：<完整 schema>
硬性要求：枚举值必须用英文原值，不要翻译
```

实测：加上 schema 后，原本失败的中文枚举一次就修正了。

## 代码骨架

```java
LlmRequest req = new LlmRequest(provider, model, messages, 0.1, null,
        ResponseFormat.jsonSchema("fault_report", SCHEMA));

FaultReport report = new StructuredOutput(client).parse(
        req, FaultReport.class,
        r -> r.equipment() != null && !r.equipment().isBlank());
```

`StructuredOutput` 内部：prepare（补模式+schema）→ chat → decode → 失败则带修复消息重试一次。
