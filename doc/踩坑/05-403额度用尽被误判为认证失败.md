# 踩坑 05｜403「免费额度用尽」被误判成「认证失败」

**日期**：2026-11-21　**项目**：llm-client-demo　**严重度**：高（设计层面）

## 现象

切换 qwen 后，`qwen-plus` 调用失败，程序归类为：

```
[AUTH][qwen] HTTP 403 -> {"error":{"message":"Free quota exhausted..."}}
可重试？false
→ 检查 API Key 是否正确、是否过期
```

提示让我去查 key，但 key 完全没问题——是**账号的免费额度用完了**。

## 原因

问题出在错误映射的写法。最初是这样的：

```java
case 401, 403 -> LlmException.Kind.AUTH;
```

**假设「403 = 没权限 = key 有问题」**，这在大多数 API 里成立，但：

- OpenAI 用 429 表示限流、402 表示欠费
- 阿里云 DashScope 用 **403 + `AllocationQuota.FreeTierOnly`** 表示「仅免费额度模式且已用尽」
- 各家对同一个 HTTP 状态码赋予的业务含义**并不统一**

**根因**：HTTP 状态码是传输层的语义，不是业务语义。403 只说明「服务器拒绝执行」，至于为什么拒绝，要看响应体。

## 解决

改成 **「先语义，后状态码」** 的判断顺序：

```java
boolean quotaIssue = lower.contains("quota")
        || lower.contains("insufficient")
        || lower.contains("balance")
        || lower.contains("arrears")
        || lower.contains("billing")
        || lower.contains("free tier");

if (quotaIssue) {
    kind = QUOTA_EXCEEDED;          // 优先按响应体语义判定
} else {
    kind = switch (status) { ... }; // 再按状态码兜底
}
```

并新增枚举：

```java
public enum Kind {
    AUTH,              // key 无效、没权限
    QUOTA_EXCEEDED,    // 余额/免费额度用尽 —— 去充值，重试无用
    RATE_LIMIT,        // 限流，可重试
    ...
}
```

`retryable()` 里 `QUOTA_EXCEEDED` 明确返回 `false`——**没钱了重试一万次也没用**。

提示语也改成了：

> → 余额不足或免费额度用尽：去控制台充值，或关闭「仅免费额度」模式，或换一个还能用的模型

并且补了测试：

```java
@Test
void quota_mapsToQuotaExceeded() {
    // 403 + quota 关键字 → QUOTA_EXCEEDED，不是 AUTH
    assertEquals(LlmException.Kind.QUOTA_EXCEEDED, e.kind());
    assertFalse(e.retryable(), "没钱了重试也没用，得去充值");
}
```

## 以后怎么避免

1. **错误映射的顺序永远是：响应体关键字 → 状态码兜底 → UNKNOWN**
2. 每接一家新厂商，就把它文档里的错误码表**补进映射规则**，并加一条测试
3. 枚举的 `Kind` 要按**处理动作**划分，不是按 HTTP 码划分——AUTH 是「改配置」、QUOTA 是「去充值」、RATE_LIMIT 是「等一下重试」，动作不同才是不同类型的错误

## 为什么这条最有价值

这是 5 条踩坑里**唯一一条不是「操作失误」而是「设计缺陷」**的。

它说明一件事：

> 统一客户端真正难的不是「把 4 家 API 调通」，而是**把 4 家的错误语义抹平成一套**。
> 这层做不好，线上出问题时你会拿到一个「HTTP 403」，然后花两小时去查根本不存在的 key 问题。
